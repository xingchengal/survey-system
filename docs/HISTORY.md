### 1.4 轮次详注（按轮检索；每轮 3~5 行）

> 表格是快索引，这里补每轮的**触发 / 做法 / 结果 / 教训**。只写原文有据的内容；原文没写的不编。

**第一轮 · 2026-09-22 · 安全与逻辑修复（9 个文件）**
- **触发**：走读发现未登录能读任意问卷、登录态横向越权读别人答卷、`/user/list` 把全站口令哈希发给前端、复制问卷丢跳转规则、git 里存着公开的 JWT 默认密钥。
- **做法**：密码字段改 `@JsonProperty(WRITE_ONLY)`（**不能**用 `@JsonIgnore`）；`AnswerController` 加私有 `requireSurveyOwnership` 挂 6 个数据端点（admin 放行，否则管理页遍历统计会坏）；题目接口按"已发布公开 / 草稿仅作者或 admin"分类放行；`JwtUtil` 启动校验密钥长度，默认值清空、真密钥进 gitignored 的 `application-local.yml`。
- **结果**：9 个文件；实测未登录读已发布问卷 200、读草稿 400、`/user/list` 401；`WRITE_ONLY` 没破坏反序列化（admin 登录仍成功）。
- **教训**：序列化注解选错会把注册/登录一起弄坏；顺带发现 `/user/list` 因 `avatar` 是 mediumtext，一个用户就返回 180KB —— 这个坑直到第四十四轮才真正关掉。

**第二轮 · 2026-09-22 晚 · 模板播种幂等 + AI 生成容错**
- **触发**：模板播种是纯 INSERT，多点一次模板就从 31 变 62；AI 失败被 `catch` 吞掉，`t_error_log` 一条都查不到。
- **做法**：播种前查已有模板，有就直接返回 `skipped`；AI 先判 429 再抛，重试 1 次（限流退避 3 秒），失败落 `t_error_log` 并给友好文案。
- **结果**：`POST /template-seeder/init` 变成可安全重复调用；AI 失败终于能在异常日志页看到。
- **教训**：`catch` 里只 `printStackTrace` 等于没记日志——异常要么交给全局处理器，要么自己落库。

**第三轮 · 2026-09-22 晚 · 系统统计限管理员 + 口令哈希升级**

- **结果**：任何登录用户读全站问卷数/答卷数/用户数的口子堵住；老账号无需重置密码。
- **教训**：静态扫描不知道"已修/未修"，重复报警不等于回归；平滑迁移的关键是"旧格式还能验、验过就换新的"。

**第四十五轮 · 2026-10-19 · 考试判分 + 实名 + 签到核销**

- **做法**：判分**不新增题型**（单选/多选/下拉已能承载，加题型要同步 7 处），只加"哪个选项对 + 每题几分 + 及格分"；限时/提交后显示答案/逐题对错；`require_login` 实名门；我的答卷两页；签到核销 + 公开报名名单（前 50 位、只返回称呼与时间）。
- **结果**：98 → 103；410 例 / 47 类；6 个迁移全部执行、真库冒烟通过。
- **教训**：`require_login` 只挡"提交"不挡"读题"（分享链接本来就能读题），要连读题一起挡需让白名单做可选身份解析，属另一轮。

**第四十六轮 · 2026-10-19 · 模板分类 + 共享分组 + 设为模板修复**
- **触发**：第六轮需求批次 1（多协作者排版）+ 模板分类遗留。
- **做法**：`t_template_category` 独立表 + 7 个预置分类 + 2 个端点；空分类可独立存在；设为模板时现场输入的新分类自动登记；共享 SQL 多 JOIN 出作者/我的角色/共享时间，前端按作者分组 + 角色筛选 + 搜索；修"点设为模板却问取消模板"。
- **结果**：103 → 105；表 21 → 22；`9e77da8`。
- **教训**：分类不能从模板反推；"我的问卷 → 更多"从白底菜单改成与行内按钮同风格胶囊（白底菜单在彩色行里像半成品）。

**第四十七轮 · 2026-10-19 · 次级管理员 + 逐人授权 + 超管保护**
- **触发**：第六轮需求批次 2（权限地基 + 禁止删超管）。
- **做法**：`subadmin` + `t_user_permission`（按用户存）；32 个管理端点 27 换 `@RequirePermission`、5 个保留超管专属；`Role.isStaff` 只用于数据范围；超管四入口一律 400（即使调用者也是超管）；前端管理工作台 + 菜单按权限过滤 + 权限点不透传。
- **结果**：105 → 110；表 22 → 23；440 例 / 49 类；真库冒烟 8 项（含"降级后旧 token 立刻 403"）。
- **教训**：漏挂注解=默认放行；前端隐藏只是体验层，四个入口的 400 用例必须都在测试里。

**第四十九轮 · 2026-10-19 深夜 · 反馈 / 客服拆分 + 线程排版**
- **触发**：两个入口共用一套工单线程、只靠 type 区分，用户感知完全重叠；详情抽屉消息区与输入框同层滚动，消息一多就要滚到底才能输入。
- **做法**：反馈收成一屏提交式意见箱（入口是顶栏铃铛旁的小图标，满意度选填 + 建议必填，提交即完成、不列工单；管理员回复从消息中心通知、点开只读查看）；客服独立成帮助中心（服务时间 + 静态 FAQ 搜索）+ 在线客服（只列 SERVICE，3s 轮询），投诉直接写成 FEEDBACK、去掉与在线客服重叠的申请协助；管理端反馈只保留「待处理 / 已处理」与回复，不出现关闭工单；线程抽 `FeedbackThread.vue` 供用户端两页与管理端复用，固定 header / 消息区独立滚动 / 首字头像 / 5 分钟分组 / 居中关闭标签 / Enter 发送；同批把页面硬编码浅色（卡片底 / 文字色 / 分隔线）统一换成主题令牌，并补消息中心、公告弹窗、抽屉与彩色浅底的深色覆盖。
- **结果**：不改表、不加端点；前端 26 → 27 页面、28 → 29 路由；后端 468 → 470 例（通知 link 按工单类型分流）。
- **教训**：伪实时线程必须按"消息方向 + 5 分钟"分组，否则同角色连续消息堆成一堵墙；中文输入法的 Enter 是组合确认，不判 `isComposing` 会误发送。

**第五十轮 · 2026-10-19 深夜 · 批次 4 个人中心**
- **触发**：第六轮需求第 5 条（功能 + 装饰 + 新手引导），等反馈/客服菜单定稿后做。
- **做法**：两个个人中心页同步加「我的待办」（草稿 / 未读通知 / 反馈 / 答卷，点击直达；未读通知用 `dsh:open-notify` 事件让布局打开消息中心）、身份卡权限范围（超管「全部权限」/ 次级管理员列出已分配模块）、使用足迹；新增零依赖 `GuideTour.vue`，选择器定位 + 聚光灯，目标不存在自动跳步；引导只在点「新手引导」时启动，不做自动弹出。
- **结果**：不改表、不加端点、页面数不变；后端测试仍 470 例；eslint / vite build 通过。顺手修「最近登录」时间字段错名（前端读 `createdTime`、后端是 `createTime`，时间列一直空白），并改为相对时间 + IPv6 回环归一「本机」；注册时间去掉了 ISO 的 `T`。
- **教训**：自动弹出式引导在"用户没点完成就离开"时会反复触发，改为手动入口更稳；引导步骤必须容忍角色差异（无权限卡片不存在时自动跳过）。

## 二、关键决策记录（ADR 风格）

> 每条四段：**背景 → 决策 → 理由 → 代价 / 放弃的方案**。这些决策**不需要再论证一次**；要推翻时先读完"代价"那一段。

### ADR-01 客服中心用「伪实时工单聊天」，不用 WebSocket（2026-10-19）

- **背景**：反馈中心 + 客服中心是第六轮需求里 ROI 最高的一条，但"客服"很容易被理解成 IM。
- **决策**：两张表（`t_feedback` 工单头 + `t_feedback_message` 消息线程）、约 11 个端点；前端 3 秒 HTTP 轮询 `?afterId=`，弹窗不可见时暂停、切回立即补拉；失败退避 3/5/10/20 秒封顶；发送带 `clientMsgId` 幂等；静态 FAQ + 纯文本，不做文件上传、不做"客服在线"绿点。
- **理由**：本质是"工单线程 + 轮询"，不是 IM；延迟 2~3 秒在客服场景可接受；省掉在线状态、心跳、断线重连与部署改造。
- **代价 / 放弃的方案**：放弃真 WebSocket IM（+5~8 天且运维复杂度上一个台阶）；不做富文本/图片/语音；轮询带来约 20 次/分钟/会话的额外请求（需对 POST 消息限流）。

### ADR-02 次级管理员做「模块级全量」，不做行级授权（2026-10-19）

- **背景**：需求是"给不同次级管理员分配不同权限"，可选做法是模块级或"只给某几个模板/某分类"。
- **决策**：角色只有 `admin` / `subadmin` / `user`；权限点 13 个（9 个可分配），按**用户**存 `t_user_permission`；有 `template:manage` 就能管**全部**模板，有 `survey:manage` 就能管**全部**问卷。
- **理由**：行级要再加 `t_admin_scope` 与每处列表/详情的过滤，工期 +3~5 天；按用户勾选比"给每人建一个角色 + 角色 CRUD 界面"直观得多。
- **代价 / 放弃的方案**：无法"只给他某一个分类"；`Role.isStaff` 只能用于数据范围，绝不能当"管理员全权"用——否则反馈管理员也能改任何问卷。以后若真要做行级，必须单独一轮。

### ADR-03 匿名答卷**不做**防重（2026-10-10）

- **背景**：答卷防重缺口被点名为开发问题；登录态确实存在 check-then-act 并发缺口。
- **决策**：登录态一律拦住（400「你已经提交过这份问卷」）；匿名侧**有意不查重**，只靠"匿名提交 30 次/分/IP"限流兜底；唯一键 `uk_survey_user (survey_id, user_id)` 落库。
- **理由**：按 IP 去重会误伤 NAT/公司网/校园网后的同网用户（"一个人交完全班交不了"）；MySQL 唯一索引**不约束 NULL**，匿名行 `user_id` 为 NULL 天然不受限——正好与规则一致。
- **代价 / 放弃的方案**：脚本仍可灌匿名答卷；绝不能执行 `UPDATE t_answer SET user_id = 0`（那会把匿名侧变成"全局只能交一份"）。前端防重复提交 + 限流覆盖真实用户。

### ADR-04 撤销「资料公开」，但**保留** `t_user.profile_public` 列（2026-10-10 / 2026-10-18 定案）

- **背景**：需求方撤销"资料公开"开关，要求把对应代码剔除。
- **决策**：端点 `PUT /api/user/profile-public`、Service/Mapper 方法、实体字段、两个页面的开关与样式、`api/user.js` 封装**全部删除**（68 → 67 端点）；**库里那一列不删**，实体故意不再映射，`init.sql` 标【已废弃】；前端页签保留并改名「账号注销」。
- **理由**：删列不可逆，收益只是"少一列"；保留列的代价仅是库里多一列。
- **代价 / 放弃的方案**：有人会在 `SELECT *` 里继续看到它（因此第四十四轮把 `findById` 改成显式列时**明确排除**了它）；**不要再把它当待办问一遍**（用户 2026-10-18 已决定保留）。

### ADR-05 只保留「唯一超管」，不新增 `is_super` 列（2026-10-19）

- **背景**：需求 4「禁止删超级管理员」要先定义"谁是超级管理员"。
- **决策**：`role='admin'` 本身就是超级管理员；`@RequireAdmin` 收窄为**超管专属**；超管不依赖 `t_user_permission`（`PermissionAspect` 兜底放行）；四个入口（个人中心注销、管理端删除、禁用/解禁、降级）对 admin 一律 400，**即使调用者也是超管**。
- **理由**：再维护一个布尔值会与 `role` 形成双口径；当前只有一个超管账号，规则简单可验证。
- **代价 / 放弃的方案**：多超管需求要先重新定义"互删/互降"规则，所以本轮明确不做；`Role.isAdmin` 不能批量替换成 `isStaff`（`DocAccessFilter`、`AdminCheckAspect`、`PermissionAspect` 必须保持超管语义）。

### ADR-06 矩阵/排序/NPS 单独一轮，题型号只追加（2026-10-18）

- **背景**：第三十八轮交接把"新题型"列为下一轮首选，但三种题型都会动答题数据结构与统计口径。
- **决策**：单独一轮（第三十九轮）做；题型号在 `QuestionType` 追加 `MATRIX(8)/RANKING(9)/NPS(10)`，**绝不复用**旧数字；矩阵行列存 `t_question.matrix_rows/matrix_cols`（JSON 文本），**不塞进 `t_option`**；排序答案存 `t_answer_detail.rank_no`，矩阵行存 `row_key`；进阶题型包 2 点/份（幂等键 `advanced-types:{surveyId}`）。
- **理由**：`t_option` 是"一维候选答案"语义，塞进行/列后每一处读选项的代码都要先过滤，漏一处就把列当答案；统计口径是 SQL `GROUP BY`，拼 JSON 就只能把整题答案拉进内存再解析。半做会破坏既有测试与统计。
- **代价 / 放弃的方案**：编辑器/填写页/统计页/公开结果页/导出/版本 diff 六处都要同步；排序题 `hasOptions(9)=true` 是有意的（候选对象就是选项），但统计不能用 `GROUP BY content`。

### ADR-07 钱包只做「模拟付费」，不接真实支付渠道（2026-10-18）

- **背景**：需求明确"模拟付费"，但"额度钱包"天然会引出真实支付。
- **决策**：`t_wallet` + `t_wallet_transaction`；注册送 10 点、发布 -1、AI -3、导出 -1、高级设置包 -1/份、协作者第 3 名起 -1/人、移入回收站 +1；价格唯一出处 `WalletFeature`，前端从 `GET /wallet/pricing` 动态渲染；充值标注"模拟充值、不接真实支付"。
- **理由**：真实渠道要商户号/证书/退款审批/发票，且与"课程项目演示"的目标不成比例；把计费规则做成枚举，后续加计费项只加一个枚举 + 一处 charge。
- **代价 / 放弃的方案**：没有套餐/发票/退款审批流；模拟充值必须带幂等键（重复提交只到账一次）；`wallet:manage` 权限点长期占位。

### ADR-08 文档四分层，`HISTORY.md` 默认不读（2026-10 定稿）

- **背景**：项目积累了大量过程叙事（轮次、改造前、踩坑经过），一度写进代码注释与架构说明，导致"注释与现状不符"反复发生（第二十轮·续④一次审计就查出 25 处）。
- **决策**：四份主文档职责单一——`SPRINT.md` 待办、`docs/ARCHITECTURE.md` 铁律、`docs/AUDIT.md` 事实矩阵、`docs/HISTORY.md` 历史归档；**过程叙事只进 HISTORY**；HISTORY 默认不读，只在四类场景按关键词检索；它不是现状依据。
- **理由**：历史信息会污染对现状的判断（"注释说 65 个端点"比"没有这条注释"更危险）；把过程与事实物理分开，才能让 AUDIT 保持"可核对"。
- **代价 / 放弃的方案**：需要分流纪律（写错地方要搬）；HISTORY 里的数字必然过期，必须靠"当时"标注与"以代码/AUDIT 为准"的免责声明兜住；旧交接文档不删，归档到 `archive/` 而不是删除（`修改记录` 是唯一过程证据）。

## 三、主题复盘

> 每节四段：**问题 → 做法 → 结果 → 教训**。事件与数字都是当时值。

### 3.1 权限与 RBAC（subadmin / 逐人授权 / 超管保护）

- **问题**：40+ 个端点曾各自手写 `if (!"admin".equals(role))`，历史上两次真实漏加校验（`/survey/statistics`、`/survey/system-overview`、`/answer` 系列），漏了不会有任何提示。第四轮全量审计又发现 4 处"签名里连身份参数都没有"。
- **做法**：先注解化（`@RequireAdmin` + `AdminCheckAspect`），再做 RBAC（`t_role` / `t_role_permission` / `t_user_role` / `t_survey_collaborator` + `@RequirePermission` + `PermissionAspect` + `OwnershipGuard`/`SurveyAccessService`），最后加 `subadmin`（`t_user_permission` 逐人授权）。
- **做法细节**：`@RequireAdmin` 只认 `admin`（超管专属）；模块端点改挂 `@RequirePermission`，32 个管理端点里 **27 换 / 5 保留**（演示数据、模板播种、异常日志删除等）；超管兜底放行，次级管理员只认被授予的点；越权抛 `ForbiddenException` → **403**，归属不符仍是 **400**（有意区分）。
- **结果**：第四十七轮收口时 110 端点（公开 13 / 需登录 34 / 归属 26 / 管理 37）、440 例 / 49 类全绿；真库冒烟验过"次管能进模板、对普通问卷 400、超管删自己 400、降级后旧 token 立刻 403"。
- **教训一**：漏挂注解就是**默认放行**（`@RequireAdmin` 不再兜底），新端点必须自己同步 `EndpointAuthMatrixTest` 的 `ALL_ENDPOINTS`/`ADMIN`/计数与审计表。
- **教训二**：矩阵测试只能证明"已登记端点"的档位；前端隐藏按钮只是体验层，安全必须在 Service 层（`deleteUser`/`setDisabled`/`deleteAccount`/`restoreUser`/`AdminManagementService` 五处都要保留 400 用例）。
- **教训三**：`Role.isStaff` 只用于数据范围（`staffModuleAllows` 只放行 `survey:manage`（全部）与 `template:manage`（仅模板）），扩大它等于给反馈管理员开问卷编辑权。
- **教训四**：权限点字符串是库、注解、审计表三处对齐的锚，**不要改名**；`ADMIN_GRANTABLE` 是"能否授给次管"的唯一口径（9 个），对象级 4 个不能在这里发。

### 3.2 统计缓存与限流（预聚合、降级方向相反、熔断）

- **问题**：统计页每次重算、2 万答卷量级下单题分布 QPS 只有 165、P50 191ms；限流原本是进程内计数，双实例各算各的。
- **做法**：单题分布/填空文本/答卷数做预聚合缓存（**不缓存**整卷统计与答卷列表）；key 唯一出处 `RedisKeys`，`survey:cache:*` 与 `survey:rate:*` 物理隔离；提交端用 Lua "**仅当 key 存在时** `INCR`"，分布/文本直接 `DEL`；所有缓存动作放在**事务提交之后**（`afterCommit`）；限流改成 Redis `INCR` + 首次 `PEXPIRE` 同一脚本原子完成；加熔断（失败一次短路 10 秒）并把 `spring.data.redis.timeout` 从 2000ms 调到 500ms。
- **结果**：单题分布 QPS 165 → 2333（P50 190 → 11ms，×14）；答卷数 ×2.2；填空 ×2.0；两条未接缓存接口数字完全不变（对照组）。2026-10-18 复测：单题分布 ×16.8、整卷统计 ×35.9、答卷数 ×2.3、填空 ×1.9，两个对照组仍不变。
- **结果（降级）**：Redis 停机时接口仍 200，但每请求要等一次 Lettuce 超时，单请求从 12ms 涨到约 **4000ms**；加熔断后第 1 次 525ms、之后 12ms，恢复后自动关闭。
- **教训一**：**缓存与限流的降级方向相反**——缓存不可用要 fail-open（回源仍服务），限流不可用必须 fail-closed（回退进程内计数，**绝不放行**）。写反一次就是"Redis 一挂全站不限流"。
- **教训二**："只是变慢"的降级会占满 Tomcat 线程池，效果等同宕机；必须有熔断，且超时值决定"第一次失败要等多久"。
- **教训三**：直接 `INCR` 会在 key 不存在时造出"答案是 1"的假缓存；必须 Lua 判存在再自增，`INCR` 失败时顺手删 key。
- **教训四**：两套统计口径（含/不含可疑样本）必须两套 key（`qstats` / `qstats-valid`），失效时**成对删**，漏一个就出现"剔除了样本、图表还是全量"的静默错误。
- **教训五**：命中率低不是缓存的问题——2 万答卷前收益为 0，所以先造夹具拿基线再决定改不改。

### 3.3 问卷版本（快照、50 版、回滚限制）

- **问题**：`QuestionService.saveQuestions` 是**全量覆盖**语义（前端发整个题目数组，后端重排 sortOrder、删掉本次没传的题），一次误操作就可能改掉题目结构，且没有任何历史可查。
- **做法**：新增 `t_survey_version`（13 张表），快照存 `questions_json` + 标题/描述 + 题数 + 摘要；**只有题目结构变化才生成**，内容没变不生成，改标题不生成；每卷保留 **50 版**，超出按版本号阈值删最旧；回滚 = 全量写回 + **生成一个新版本**（历史线性、可审计）；diff 按 `questionId` 对齐；跳转目标指向"会被重新创建的题"时 **400 拒绝回滚**。
- **实现细节**：`capture` 在保存题目的**同一事务**里（保存回滚，快照也不留），`saveQuestions` 拆成 `@Transactional` 三参重载 + private `doSaveQuestions`，两个重载**互不调用**（同类内部调用会让事务注解失效）；`SurveyVersionService` 不注入 `QuestionService`（避免成环）；快照反序列化允许未知字段；列表与详情分两条 SQL（`questions_json` 是 MB 级大字段）。
- **结果**：4 条端点（全"需登录 + 归属"），`SurveyVersionServiceTest`(9) + `QuestionServiceRollbackTest`(4)；真库实测 v1(2 题) → v2(3 题) → 回滚生成 v3(2 题)，题干恢复、新题删除。
- **教训一**：回滚遇到悬空跳转时**宁可 400 说清原因，也不静默置空**——静默置空会让用户以为回滚成功，而答题页走到那里会"找不到目标就提前结束"。
- **教训二**：版本号是**业务号不是行号**，裁剪旧版后不能回退编号。
- **教训三**：`questions_json` 别在列表接口里 `SELECT *`，会白传几十 MB。
- **已知局限**：回滚修不了"跳转指向被删题目"；只记录题目结构；早期历史会被滚动丢弃；回滚会删掉"新版才有的题"，其答卷明细成为孤儿（与手工删题一致）。

### 3.4 答卷质控（四条规则、只打标）

- **问题**：答题时长过短 / 全选同一项 / 前端矛盾 → 无效样本会污染统计，但自动删又会误伤。
- **做法**：`t_answer` 加 `duration_ms` / `quality_flag` / `quality_reasons`；四条规则——`TOO_FAST`（耗时 < 题数 × 1500ms）、`STRAIGHT_LINE`（≥3 道选择题、答案在各自选项里的位次全相同）、`OPTION_MISMATCH`（答案不在该题选项里）、`DUP_TITLE_CONFLICT`（同题干两题答案不一致），每条都配"不命中"边界；**只打标不删除**，只在**提交那一刻**算一次；新增 `GET /answer/quality/{surveyId}`，两个统计端点加可选 `excludeInvalid`。
- **结果**：真库 3 份样本里 2 份可疑（`TOO_FAST,STRAIGHT_LINE` 与 `OPTION_MISMATCH`），剔无效后题一分布从 A=2/Z=1 变成 A=1；`AnswerQualityServiceTest`(12) 覆盖四条规则 + 每条不误伤边界。
- **教训一**：**没有耗时数据时不判**——不能把"没上报"当成"很快"；只有 2 道题时不判直线（2 题同选太常见）。
- **教训二**：`duration_ms` 前端上报、可伪造，只能作质控提示，**不能当安全边界**。
- **教训三**：不回算历史答卷——否则同一份答卷今天有效、明天无效，用户无法解释图表变化。
- **教训四**：语义矛盾（"没孩子却填了孩子年龄"）需要题目间约束规则，属产品能力，不硬装成 AI 质检。

### 3.5 钱包（幂等、并发、对账）

- **问题**：额度体系一旦扣错/超扣/重复扣，用户信任直接崩塌；50 并发是必须过的线。
- **做法**：`t_wallet`（余额/冻结/version）+ `t_wallet_transaction`（有符号 `amount` + `idempotency_key` 全表唯一 + `balance_after` 快照）；扣减用 `UPDATE ... WHERE balance >= ?` 原子完成；**先 `SELECT ... FOR UPDATE` 锁钱包行，再写流水**；幂等键覆盖 `publish:{surveyId}`、`refund:{surveyId}`、`signup:{userId}`、`ai:{uuid}`、`advanced:{surveyId}`、`collab:{surveyId}:{userId}` 等；对账口径 `SUM(amount) = balance`，只报告不自动修。
- **结果**：`WalletServiceTest`(15) + 真库 `WalletConcurrencyTest`（50 并发不超扣 / 同幂等键只扣一次 / 对账一致）；端点 87 → 93 → 94。
- **教训一**：锁顺序反了会死锁——最初"先插流水、再抢钱包行锁"，50 并发实测 **46 个** `DeadlockLoserDataAccessException`；改成先锁钱包后全绿。资金类操作必须固定这个顺序。
- **教训二**：`INSERT IGNORE` 建钱包会加共享锁，再升级 `FOR UPDATE` 时两个并发事务互相等；正确做法是**先 `FOR UPDATE` 查，查不到才插入**。
- **教训三**：计费放在**保存事务内**（所有校验之后），余额不足让整次保存回滚；不要在 Controller 里扣（会扣了钱没存上题）。
- **教训四**：价格唯一出处是 `WalletFeature` 枚举，前端从 `pricing` 动态渲染，别再硬编码；流水时间用 `@JsonFormat`，管理端 Map 用 SQL `DATE_FORMAT`，否则页面出现 ISO 的 `T`。

### 3.6 模板与协作（分类、共享分组）

- **问题**：模板分类原本是自由文本（只能从现有模板反推）、没有使用热度；"共享给我的问卷"是一张平铺列表，看不出作者是谁、我是什么角色。
- **做法**：新增独立表 `t_template_category`（7 个预置分类 + 存量回填，**空分类可独立存在**，设为模板时现场输入的新分类自动登记）；`t_survey.template_use_count` 记热度（只统计"从模板创建"这条路径）；`findSharedSurveys` 多 JOIN 出 `ownerUsername/ownerNickname/myCollaboratorRole/sharedTime`，前端按作者分组 + 角色筛选 + 标题搜索；协作者三种角色 viewer/editor/analyst，前 2 名免费、第 3 名起 1 点/人。
- **结果**：第四十轮模板使用次数可排序、分类概览 chips；第四十六轮模板分类独立成表（表 21 → 22，103 → 105 端点）；「设为模板」弹窗文案反转（点"设为模板"却问"取消模板"）修掉。
- **教训一**：分类**不能从模板反推**——空分类要能存在，否则"先建分类再放模板"的流程走不通。
- **教训二**：热度要钉住"哪条路径算使用"：从模板创建 +1、复制已发布问卷**不计数**、草稿拒绝；否则数字很快失去意义。
- **教训三**：协作者角色（`t_survey_collaborator.role`）与系统角色（`t_user.role`）是两套东西，改角色时别互相污染。
- **教训四**：模板管理页去掉操作列 `fixed="right"` 才修好"固定列覆盖创建时间"——表格列宽在窄屏是要逐级压的，不是加 `fixed` 就完事。

### 3.7 审计订正（**审计**：总数对、分档错、漏登记 12 条、端点下线）

- **问题**：端点审计表多次出现"合计对、分档错"，还有明细表长期漏登记；也曾按"前端零调用"误删端点。
- **做法**：立四条硬规矩——① 标题 = §二汇总 = 四张明细表活行之和 = 注解计数，**四处必须一致**；② 分档复核窗口 = "本行映射 → 本方法的 `public` 签名（遇 public 即停）"；③ 用"注解全集 ↔ 明细表活行"做**双向差集**；④ 带删除线的行是已删端点历史，不计入活行。
- **订正一（第四轮）**：原写"需登录 22 / 管理员 19"，复核后是 **21 / 20**；总数 41 一直是对的。过程中两次把数算错：先按"注解在映射上方 12 行"找只剩 14，再按"往后 25 行"又把邻居算进来 —— 因为本项目 `@RequireAdmin` 写在 `@Mapping` **之后、方法签名之前**。
- **订正二（第十九轮）**：合计曾写 64，实为 **63**（明细漏 1 条 + 差异说明算错 1 个叠加）。
- **订正三（第三十四/三十五轮）**：明细表长期漏登记 **12 条**（协作者 7 条、举报审核 5 条），于是"需登录 24 + 归属 25 = 84"与合计 86 自相矛盾；补齐后为 **需登录 26 + 归属 25 + 管理 23 + 公开 12 = 86**，第三十五轮再加 1 条 ⇒ 87。
- **订正四（第六轮）**：`publish`/`copy` 权限不足时 `return null`、其它端点返回字符串，前端分不清"没权限"和"不存在"；统一改成抛异常 → 全局处理器 → 400 + 统一 JSON。
- **事件（第十六轮，**端点下线**）**：按"前端零调用"删掉 6 条，`POST /answer/submit/{surveyId}` 也在其中。用户指出它是 `t_answer.user_id` 的**唯一写入路径**（`submit-share` 的 userId 恒为 null），删了这列就是死列，还堵死答卷防重/我的答题历史/实名问卷——**当天恢复**，并在类注释与方法 javadoc 写明"别再按零调用删它"。
- **下线时的三道保险**：① 每条删除留 `// ★ 本轮死代码清理` 注释，写明依据与"要恢复怎么做"；② `SurveyControllerRoutingTest` 在注解层钉住"删掉的映射确实没了、保留的还在"；③ 起 8081 临时实例 HTTP 实测，6 条返回 404/405，保留端点全 200。
- **教训一**：**分档错了比总数错了更隐蔽**（`22+19` 与 `21+20` 都等于 41），只有逐条提注解 + 双向差集才能发现。
- **教训二**："前端零调用"不等于"应该删"——它可能是**唯一写入路径**或扩展点；删端点前先查"谁写这个字段"。
- **教训三**：`@RequireAdmin` 的覆盖数必须从源码位置确认，纯按行距猜，方向或跨度错一次就差 5~6 个，且看起来同样"有据可依"。
- **教训四**：审计维度是**四列**不是三列 —— 身份 / 角色 / 归属 / **业务前置条件**（问卷是否已发布、是否在回收站、是否已结束）。第四列是踩过 `submit` 往草稿问卷塞答卷之后补上的。

### 3.8 环境坑（ECJ、沙箱、CRLF、BOM、MyBatis 静默、Spring Boot 4 ObjectMapper）

- **问题**：这台机器上"命令成功"与"真的生效"经常不是一回事：编译假成功、构建假成功、字段静默为 null、启动才炸。
- **ECJ 假编译**：IDEA 开着时用 ECJ 做**容错编译**，把"有编译错误但能生成"的 class 写进 `target/classes`，且**时间戳与源码相同** → `mvnw compile` 说 `Nothing to compile`，运行时报 500。处理：给改过的源文件 touch 一下再 `mvnw -o compile`；或用 `javap -v` 搜 `Unresolved compilation problem` 确认。**不要删 `target/classes`**（IDEA 的 8080 正用它，含前端静态文件）。
- **沙箱**：只能写工作区，写别处报 `[sandbox: file access denied]`（这是要批准的一次性提权，不是绕过题）；禁止子进程管道 → `vite build`/`npm run dev` spawn EPERM（绕过：`npx vite --configLoader native`），Node 里连 `mysql.exe` 都取不到输出（验证脚本只做 HTTP，查库放 pwsh）；无头浏览器因 mojo 命名管道崩 → **页面视觉与浏览器交互无法验证**，只能靠 HTTP 实测 + ESLint + 构建，并如实告诉用户"这部分我没验"。
- **CRLF**：`.java`/`.vue` 是 CRLF。自己写脚本做精确替换时 `old` 里写 `\n` 匹配不上；做法是读入 `replace(/\r\n/g,'\n')` 归一，写回再还原。
- **BOM**：`Set-Content -Encoding UTF8` 会带 BOM → `java` 单文件模式报 `非法字符: '\ufeff'`，`mysql < init.sql` 直接语法报错。写 `.java` 用 `[System.IO.File]::WriteAllText(path, text, (New-Object System.Text.UTF8Encoding($false)))`，生成给别的程序吃的文件用 `cmd /c "... > file"` 或 Node 的 `writeFileSync`。
- **MyBatis 静默**：开了 `map-underscore-to-camel-case`，字段名不匹配时**不报错、不警告**，只是那一个属性恒 null（实测把 `create_time` 写成 `createdTime`，编译/单测/200 全过，只有"最近登录"时间列永远空）。所以改 `findById` 这类显式列清单时，必须用脚本比对 `information_schema.COLUMNS` vs SELECT 列表，再用真实请求逐字段核对——漏 `disabled` 会让"被禁用账号仍能登录"复活。
- **Spring Boot 4 ObjectMapper**：Boot 4 不再注册 Jackson 2 的 `ObjectMapper` bean，`@Autowired ObjectMapper` 让**启动直接失败**（`No qualifying bean of type ObjectMapper`）。要序列化就自己持有 `private static final ObjectMapper MAPPER = new ObjectMapper();`（与 `QwenClient` / `WebUtils` 一致）。同源的坑：Boot 4 的 `@AutoConfigureMockMvc`、`@MockitoBean` 都换了包，按 Boot 3 的 import 写直接编译不过。
- **其他两条高频**：PowerShell 传 `-Dfile.encoding=UTF-8` 必须整体加引号（否则被拆成 `/encoding=UTF-8`）；`git commit -m "很长多行中文"` 会被引号搞坏，改用 `git commit -F <文件>`。
- **教训一**：状态码 200 不能证明字段有值；"编译通过 + 单测绿"不能证明 class 是新的。
- **教训二**：验证顺序应当是"先测量再推断"——第二十轮·续②曾三次误判根因（怪测试时序、怪旧实例、怪 DB 缓存），最后加一行临时诊断日志一次定位。

### 3.9 反馈 / 客服与伪实时轮询（批次 3）

- **问题**：反馈与客服本质都是"工单线程"，但用户心智不同——反馈是意见箱（轻量、不承诺实时），客服是帮助中心 + 人工工单。第一版做成同一页两个 Tab、只靠 `type` 区分，用户分不出差别；线程页还把消息与输入框放在同一滚动层。
- **做法**：共用 `t_feedback` + `t_feedback_message`，`type` 区分 FEEDBACK / SERVICE；管理侧只认 `feedback:handle`，不复用 `review:handle`；用户侧按 `feedback.user_id` 校验归属。同一用户最多一个 OPEN SERVICE 用**生成列 `open_service_user_id` + 唯一索引**兜底（关闭后自动释放）；发送用 `client_msg_id` 幂等；轮询用 `afterId` 增量、单次 50 条 + `hasMore`、隐藏暂停、失败 3/5/10/20 秒退避。
- **结果**：126 端点 / 25 表 / 26 页面；反馈 11 端点、2 页面；468 例 / 51 类。反馈与客服的入口拆分、线程排版优化已立项（SPRINT P1），不改表。
- **教训**：同一套数据模型不代表同一套交互，先定用户心智再定页面；伪实时的 GET 轮询**不能与 POST 共用限流桶**（`RateLimitInterceptor.Rule` 增加可选 `method`）；MyBatis `<script>` 注解里 `<` 必须写 `&lt;`，否则上下文启动就失败。

```sql
DROP TABLE IF EXISTS t_survey_collaborator;
DROP TABLE IF EXISTS t_user_role;
DROP TABLE IF EXISTS t_role_permission;
DROP TABLE IF EXISTS t_role;
DROP TABLE IF EXISTS t_survey_review;
ALTER TABLE t_survey DROP COLUMN lifecycle;
```

- ⚠ 删 `lifecycle` 会让 `SUSPENDED` 状态消失 —— **被下架的问卷会自动"恢复"可提交**，且 `idx_lifecycle` 一并消失。回滚前先确认没有处于下架状态的问卷：`SELECT id,title FROM t_survey WHERE lifecycle='SUSPENDED';`
- 回滚后 `@RequirePermission` / `OwnershipGuard` / 协作者端点 / 举报审核台全部失效，必须同时回滚代码（`19695d0` 及第三十五轮提交）。
- 只想回滚单条举报处理：`UPDATE t_survey SET lifecycle='PUBLISHED' WHERE id=?;`（这是取消下架的等价 SQL，配套的 `POST /survey/unsuspend/{id}` 只允许 `SUSPENDED → PUBLISHED`）。

### 4.8 判分 / 实名 / 签到（第四十五轮，`migration-exam-grading.sql` + `migration-exam-p1.sql` + `migration-survey-require-login.sql` + `migration-checkin-participants.sql`）

```sql
ALTER TABLE t_survey
  DROP COLUMN grade_enabled, DROP COLUMN pass_score,
  DROP COLUMN time_limit_seconds, DROP COLUMN show_answer_after_submit,
  DROP COLUMN require_login, DROP COLUMN checkin_enabled, DROP COLUMN show_participants;
ALTER TABLE t_question DROP COLUMN score;
ALTER TABLE t_option   DROP COLUMN is_correct;
ALTER TABLE t_answer
  DROP COLUMN total_score, DROP COLUMN earned_score, DROP COLUMN is_passed,
  DROP COLUMN checked_in, DROP COLUMN checked_in_at;
ALTER TABLE t_answer_detail DROP COLUMN is_correct;
```

- 成绩、逐题对错、签到记录全部不可恢复；`require_login` 删掉后"实名问卷"退回匿名可填。
- IP 限制属第三十八轮：`DROP TABLE IF EXISTS t_survey_ip; ALTER TABLE t_survey DROP COLUMN ip_limit;`

### 4.9 个人中心 / 软删除 / 禁用 / 票据（第十九~二十轮、第四十二轮）

```sql
DROP TABLE IF EXISTS t_login_log;
ALTER TABLE t_user
  DROP COLUMN profile_public,
  DROP COLUMN deleted_at,
  DROP COLUMN disabled,
  DROP COLUMN token_valid_after;
```

- ⚠ 后三个用户列是**安全回退**，不是清理：删 `deleted_at` 会让所有已注销账号"复活"；删 `token_valid_after` 会让此前已作废的 access token 在剩余有效期内重新可用；删 `disabled` 会让被禁账号立即能登录。执行前先确认：`SELECT COUNT(*) FROM t_user WHERE deleted_at IS NOT NULL OR disabled=1;`
- `profile_public` 是历史列，删了只是"少一列"，**不建议**（见 ADR-04）。

### 4.10 性能索引（第二十八轮，`migration-perf-indexes.sql`）

```sql
ALTER TABLE t_answer DROP KEY idx_survey_submit_time;
ALTER TABLE t_survey DROP KEY idx_created_time;
```

- 回滚后答卷列表分页/质控样本/导出预检会退回全表扫；该脚本当初还删过一条冗余索引 `idx_survey_id`，要恢复需自行 `ADD KEY`（脚本里没有反向语句，属已知缺口）。

### 4.11 端点层回滚（单条上线 / 单条下线）

- **下线一条端点**：删映射 → 审计表对应行加删除线（不计入活行）→ 同步 `EndpointAuthMatrixTest` 三处（`ALL_ENDPOINTS`、`ADMIN`、计数算式）→ `mvnw -o test`。
- **恢复一条端点**：反向操作；第十六轮删掉的 6 条都在代码里留了 `// ★ 本轮死代码清理` 注释，按注释里的"要恢复怎么做"恢复。
- **验证**：`git status` 应只有预期文件；起 8081 临时实例打真实 HTTP，**验证完按端口 `Stop-Process`**（`job_kill` 杀不掉 maven fork 出的 java）。

### 4.12 尚未建的功能（无可回滚对象）

- **反馈中心 / 客服**：库里没有 `t_feedback` / `t_feedback_message`，`sql/` 下也没有 `migration-feedback.sql`。执行前确认（应返回空）：

```sql
SELECT table_name FROM information_schema.tables
WHERE table_schema='survey_db' AND table_name LIKE 't_feedback%';
```

- **测评（量表计分）**：只有《问卷系统-测评方案-草案.md》，无表、无端点、无迁移。
- 这两项若将来落地，回滚脚本必须**先写进 `sql/migration-*.sql` 的注释里**再执行（本项目所有迁移都遵守这条）。

## 五、已删除/已撤销的东西（**端点下线**）

> 本节是"曾经存在、现在没有"的清单。分三类：**代码删了但有残留**、**端点下线**、**需求撤销**。恢复成本从低到高排列。

### 5.1 「资料公开」（`profile_public`）

- 端点 `PUT /api/user/profile-public` 已删（**68 → 67**，第二十轮·续②）。

### 5.2 六个「前端零调用」端点（第十六轮删除，**端点下线**）

### 5.3 `POST /answer/submit/{surveyId}`：**先删后恢复**（第十六轮）

## 六、维护约定（写给下一条大肥鱼）

1. **只在两种情况写这里**：完成一个可归档阶段；或用户明确要求补历史。不做日常待办更新（那是 `SPRINT.md`）。
2. **写什么**：§1.1 追加一行轮次摘要（3~8 行内能说清），§3 对应主题追加"问题→做法→结果→教训"；有 commit 就记，没有就写 `—`。
3. **不写什么**：不逐字复制《问卷系统-修改记录.md》（那是 4400 行过程日志，证据留在工作区）；不写"现状待办"与"架构铁律"（各有归属文档）。
4. **数字一律标"当时"**：HISTORY 的数字会过期，过期不是错误，**装作现值才是错误**。
5. **结论被推翻时**：新增一条"订正"并指回旧条，**不修改旧正文**；历史的价值在于它诚实地记录了当时的判断。
6. **每次改完自检**：`wc -l docs/HISTORY.md`（体量控制在 600~900 行）；grep 一遍新加的轮次号与 commit，确认没有把"当时"当"现在"。
7. **与另外三份的边界**：可复用工程约束 → `docs/ARCHITECTURE.md`；未决事项 → `SPRINT.md`；端点/表/测试/页面事实 → `docs/AUDIT.md`；过程与决策 → 这里。

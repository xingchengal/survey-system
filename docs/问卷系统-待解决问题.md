## A. 需要你决策（3 项）

### A1. 答卷防重的**并发缺口**（要动表结构 —— ★ 旧结论已订正，别再按旧文档做）

**现状（已在代码里）**：`AnswerService.submit` 按 `survey_id + user_id` 查重，
登录用户重复提交 → 400「你已经提交过这份问卷，不能重复提交」；**匿名侧有意不查重**（按 IP 去重会误伤 NAT 后的同网用户）。

**缺口**：这是 **check-then-act** —— 两个请求同时通过检查、各插一条，就能灌进两份。
正常用户双击概率极低（前端有防重复提交），脚本可以稳定复现。

**★ 正确修法（一句话就够，不需要改产品规则）**：

```sql
-- 加之前先确认没有历史重复行（有就先人工处理，否则 ALTER 会失败）：
SELECT survey_id, user_id, COUNT(*) c FROM t_answer
WHERE user_id IS NOT NULL GROUP BY survey_id, user_id HAVING c > 1;

ALTER TABLE t_answer ADD UNIQUE KEY uk_survey_user (survey_id, user_id);
```

★ 为什么这就够了：**MySQL 的唯一索引不约束 `NULL`** —— 匿名答卷的 `user_id` 是 `NULL`，
天然不受这个唯一键限制，正好与"匿名不防重"的现有规则**一致**。
⇒ 旧版文档里那套"先把匿名 `user_id` 改成 0、再建唯一索引、于是必须先改产品规则"的推演是**错的**，
**不要**执行 `UPDATE t_answer SET user_id = 0`（那才会把匿名侧变成"全局只能交一份"）。
这一步的口径已写进 `AnswerService.submit` 第四道守卫上方的注释。

**为什么现在没做**：`ALTER` 要动**你的库**，按本项目惯例（改库一律先征求你同意）我不擅自动你的库。
现状已有"应用层查重 + 前端防重复提交 + 匿名提交 30 次/分/IP 限流"覆盖绝大多数真实场景。
**加不加、什么时候加，你定**；给一句话我就把语句补进 `sql/init.sql` 并单独出一份 ALTER 脚本。

### C3. 安全/健壮性的已知局限（都写明了理由，没有偷偷留着）

| 项 | 现状与理由 |
|---|---|
| 匿名答卷无幂等 / 无问卷级频控 | 公开接口 + 分享码泄露即可反复灌水，污染"答卷数/选项分布/词云"。现有的是全站级限流，挡不住"每 IP 少量多次"。要做得先定产品规则（见 A1） |
| `RequestSizeFilter` 挡不住刻意用 `chunked` 的请求 | 它按 `Content-Length` 拦（这是主要防护目标：声明了超大 body 的请求）。没有 `Content-Length` 时**放行 + 记 warn** —— 因为一律拒绝会误杀 publish/view/logout 这类无 body 的 POST（实测踩过）。要堵 chunked 得再包一层限制读取字节数的 `HttpServletRequestWrapper`，风险与成本更高 |
| 「不能删最后一个管理员」是 check-then-act | 两个管理员并发互删时理论上都能通过 `countAdmins() <= 1`。当前唯一入口下**不可达**（能执行删除的人自己必然是管理员 → 他删自己时已被前一道检查拦住），严重度低 |
| 彻底删除问卷/删用户不清理指向它的站内通知 | 通知里存的链接是 `/my/surveys/{id}/statistics`，问卷删了以后那条"收到新答卷"还留着，点进去必然"问卷不存在"，未读红点也会一直算它。低优先级；修法是级联时删掉 link 含该 id 的通知，或给 `t_notification` 加 `survey_id` 列（比 LIKE 干净） |
| 定时任务"先查再改"非原子 | 多实例部署会重复发布 / 互相覆盖分享码（当前是单实例，无影响）。要上多实例：改成条件 `UPDATE ... WHERE status = 0` 并看受影响行数，或 `SELECT ... FOR UPDATE` |

### C5. 体验瑕疵：滑块"长时间无操作自动刷新"**未实现**（需求第 3 条要求过）

当前只有**页面加载 / 手动刷新 / 失败 3 次**三种换图时机，没有空闲计时器。
而后端凭证 **60 秒就过期** —— "用户盯着图不动 90 秒再拖"时，拖动**看起来成功**（前端组件自己判定通过），
但提交注册必然拿到「滑块验证已失效，请重新拖动」。**这已经是可感知的问题**，只是不常见。
建议修法（两条一起做才完整）：① 提交前检查"取图到提交是否超过 55 秒"，超了就静默换图 + 提示；
② 在卡片上挂 mousemove/mousedown，60 秒无操作 → 重新取图。

> 顺带一条**别改回去**的事实：组件自带的刷新图标（`@refresh`）**只复位滑块、不重新取图**，
> 所以"点刷新图标换一张图"实际是靠 `:key="sliderToken"` 重建组件 + 新 `bgImage` 实现的。
> 若再监听 `@refresh` 去调取图方法，会白多打一次 `/slider`（多消耗一次限流额度）。

## E. 收工时的库基线（判断"有没有留下垃圾"用）

**一条命令自查**（口令见 `application-local.yml`）：

```powershell
mysql.exe -uroot -p<口令> --default-character-set=utf8mb4 survey_db -e "source C:/Users/1/Desktop/dsh/IdeaProjects/sql/baseline-check.sql"
```

★ **这行不要写死数字**：库是**活的** —— 你会继续在自己的 8080 实例上测，
第四轮期间就连着做了"注册 → 注销账号 → 管理员恢复 → 重新登录"，`t_user` 因此多出一个账号，日志跟着涨。

两条判断口径（都是踩出来的）：

1. **数字变大通常是用户自己测的**，先看 `t_operation_log.username` / `create_time` 与
   `t_answer.submit_time`，判断**是谁、什么时候**造的，再决定动不动；读操作日志页本身也会记一条日志，别误删。
2. **`COUNT(*)` 与 `MAX(id)` 不是一回事**（历史上删过日志）：清测试数据一律**按 id 区间**删，不要按条数。
   反过来，**判断"有没有测试账号残留"要按 `username` 查**，不要按 id 区间（你自己建账号会让 id 跳跃）。
